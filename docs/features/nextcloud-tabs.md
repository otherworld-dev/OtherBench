# Nextcloud tabs

Spec: `docs/superpowers/specs/2026-10-22-nextcloud-tabs-design.md`. Code mode's right panel has three more tabs, **Deck**, **Wiki** and **Links**, which show an app's Deck board, its Collectives pages and its tagged bookmarks from Adam's Nextcloud. The tab order is now Issues, Deck, Wiki, Links, Files, Terminal, Chat, and tabs that don't fit the panel's width go under a **More tabs** (») menu (`visibleTabs.ts`), with the selected tab always kept in the strip. The calls follow `nc.py` (`E:/Git/Nextcloud-CLI`), which already works against the real server, rather than Nextcloud's documentation where the two differ.

- **Where it lives.** Migration `030-app-nextcloud` adds four synced columns to `app`: `deck_board_id`, `wiki_collective`, `wiki_page_path` and `bookmark_tag` (`deckBoardId`, `wikiCollective`, `wikiPagePath`, `bookmarkTag` on `App`). The collective and page path are set together or not at all. The Nextcloud URL and user are not synced: they are a machine-local `app_setting` (`nextcloud`, `{ baseUrl, user }`), and the app password is in the `SecretStore` under `nextcloud:password`. The app form (`views/AppView.tsx`) has a board picker, the collective, the page path and the tag, and when a folder is picked it fills any field left blank from the "Project links" section of the folder's `CLAUDE.md` (`core/src/domain/project-links.ts`, read through `GET /api/nextcloud/detect-links`), so an app made from one of Adam's repos is linked up without typing anything. **Fill from CLAUDE.md** does the same over what is already there.
- **Server.** `packages/server/src/nextcloud/`:
  - `client.ts` is the only code that talks to Nextcloud. `httpNextcloudClient` builds the Deck (`api/v1.0`), Collectives (OCS, `{ ocs: { data } }`), WebDAV (page text) and Bookmarks (REST v2, `{ status, data }`) calls, and every request carries Basic auth, `OCS-APIRequest: true` and a 15 s timeout. A failure is a `NextcloudError` with a fixed message and the HTTP status, never the response body. Only a 401 is `nextcloud-auth`. Deck answers 403 for a board or card the account can no longer see (unshared or trashed), so a 403 is `nextcloud-not-found` ("That isn't in Nextcloud any more, or this account can't see it."), which also means a stale preferred board doesn't stop a card on another board from being found.
  - `deck.ts`, `wiki.ts` and `bookmarks.ts` are the operations over that client: the board view (columns in board order, the archived cards, the labels and which column is "Doing"), finding a card by id, editing, moving, Done, Reopen, Archive, labels and delete; the page tree under the app's page and one page's markdown; and the bookmarks carrying the app's tag. Done follows `nc.py deck done`: the card is moved to the board's Done column first, then marked done, then archived, so a failed move leaves it untouched. Deck has no "card by id" route, so a card is looked for on the app's board first and then on every other board.
  - `config.ts` reads the settings and makes the client. `container.nextcloud` replaces the client factory in tests.
  - `routes/nextcloud.ts` is `/api/nextcloud`: the settings (GET, PUT), `POST /test` (signs in and checks the three apps answer), the board and collective lists for the pickers, `detect-links`, and the card routes (`/cards/:cardId` GET, PATCH and DELETE, plus `move`, `labels`, `done`, `reopen` and `archive`). A card route takes `?board=` as the board to look on first, and works without it, which is what a "Deck #N" link in a chat uses.
  - `routes/app-nextcloud.ts` is mounted on `/api/apps` before `appsRoutes`: `/:id/deck` (and `POST /:id/deck/cards`), `/:id/wiki` and `/:id/wiki/pages/:pageId`, and `/:id/links` with add, edit and delete. None of these need the app's folder, so they work for an app whose folder is on another machine. An app with no board, page or tag answers `no-deck-board`, `no-wiki-page` or `no-bookmark-tag`. A board Nextcloud no longer has is a 404 saying the app's board isn't in Nextcloud any more, and a 404 on the bookmark list is `nextcloud-app-missing` (Bookmarks isn't installed), rather than a bare "HTTP 404". If a new card's `#<id> ` prefix can't be added after it was created, the card comes back without it and the failure is logged, so the user isn't invited to retry into a duplicate.
  - Every Nextcloud failure goes through `codeCall` and comes back as a `CodeRouteError`, 409 (or 404 for something not found), never a 500. The codes are in `core/src/types/nextcloud.ts`.
- **Web.** `packages/web/src/code/`:
  - `DeckTab` shows one column at a time, with a button per column and one for the archived cards, and opens on the "Doing" column (a title of `doing`, `in progress`, `in-progress` or `wip`, any case) until another is picked. A card opens in place with its description, Move to, Done or Reopen, Archive, Labels, Edit, Delete and **Start a chat on this**, which makes a new chat in the app with the card's number, title, link and description in the composer, not sent (`startChatFromCard.ts`). The `#<id> ` prefix Adam's cards carry is taken off for display and kept on a retitle. A refresh of an open card that fails shows its error above the last answer, and a card that is no longer found (deleted elsewhere) is dropped from the cache and the list is fetched again, as it is after a failed action.
  - `WikiTab` is the page tree under the app's page, with Find, and a page opened beside it as markdown. A link to another page of the tree opens it in the tab.
  - `LinksTab` lists the bookmarks with the app's tag, newest first, and adds, edits and deletes them. The app's tag is always kept on a bookmark edited here.
  - Each chat and app home keeps its own place in each tab (the column shown, the open card or page, the open folders) in the store (`deckViews`, `wikiViews`), as Issues does, and the last answers from Nextcloud are kept there too and shown while they are fetched again. The tabs refresh with `useCodeRefresh` and ↻.
  - "Deck #N" (or "Deck card #N") in a message is a link (`MarkdownBody`, `openDeckCard.ts`). In Code mode, with the focused pane in an app that has a board, it opens the card in the Deck tab, expanding the panel if it was collapsed or opening it as the overlay on a narrow window. Otherwise it opens the card in Nextcloud in the browser.
  - Settings → Nextcloud (`views/settings/NextcloudPanel.tsx`) has the URL, user and a write-only app password, and **Test**, which shows "Signed in as …" and a tick or cross for Deck, Collectives and Bookmarks. The Settings tab strip now wraps, as the extra tab pushed ✕ off a 1400 px window at 150% text size (`layout.spec.ts` caught it).
- **Security posture.**
  - **The app password stays on this machine.** It is in the `SecretStore` only (`nextcloud:password`), never in the synced DB, never in a response (the settings answer only `passwordSet`), and never in a log line or an error message. The settings field is never pre-filled. When the URL is changed to another host (a different origin) and no new password is typed, the stored one is deleted, so it is never sent to a host it was not typed for, and the same happens when a URL is set again after it was cleared.
  - **https only, except on loopback.** `normaliseBaseUrl` refuses a URL that isn't `https://`, apart from `http://` to `localhost`, `127.0.0.1` or `[::1]` (which the e2e fixture needs). A URL with a username, password, query or fragment in it is refused too, and WebDAV path segments are escaped.
  - **A move never recreates the card.** `nc.py` falls back to deleting the card and making a new one when a move doesn't take, which changes its id and breaks every "Deck #N" that points at it. Here the documented reorder route is tried, the card is checked to have really moved, then the web UI's internal route is tried, and if neither moved it the answer is `deck-move-ignored` and the card is as it was.
  - **Nextcloud's content is untrusted.** Card descriptions and wiki pages render through `MarkdownBody` with `remoteImages={false}`, so an image is never loaded (a remote image would tell its server when Adam read the page) and shows as `[image: alt text]` only, with no link to the page in Nextcloud, which the spec asked for and which is not built yet. The rendered text is wrapped in `stayInApp`, so a relative link cannot take the window away. Web links open through `openInBrowser`, `http:` and `https:` only, however `stayInApp` also lets a `mailto:` link through to the webview's default action, so a `mailto:` in a card or page opens the mail client. That is shared with the Issues tab, which uses the same `stayInApp`, and is left as it is for now. A bookmark with any other scheme is listed, but its row has no `href`, so neither a click nor a middle or Ctrl-click follows it, and the server refuses to save one.
  - **User-only, and not on the peer listener.** These are user actions on server routes, never model tools, and they are mounted only on the authed `/api`. A paired machine can't act on this machine's Nextcloud account.
- **Known gaps.**
  - **No comments or attachments** on Deck cards.
  - **The wiki is read-only.** Pages are edited in Nextcloud, and **Open in Nextcloud** on a page goes there.
  - **One account.** There is one Nextcloud URL, user and password per machine, shared by every app.
  - **The URL and user are per machine.** They don't sync, so each machine is set up in Settings on its own. The per-app links (board, page, tag) do sync.
  - **Unrelated flakes.** A full-suite run now and then fails a test once and passes on the next run (the `SandboxPanel` polling test, for example). None of these were in the Nextcloud code.
  - **Three e2e specs fail in a full Playwright run and pass on their own:** `attachments.spec.ts:150`, `slash-commands.spec.ts:27` and `layout.spec.ts:64`. They depend on what earlier specs leave on the shared server. The first two fail the same way at b99c0136 without this work's e2e changes, so they aren't from it. `layout.spec.ts:64` used to fail earlier, on Close settings being off the screen, which is fixed. It now fails later, on its thread-overflow check, and only in the full run. At b99c0136 the earlier failure stopped the test before it reached that check, so it isn't proven either way whether that one predates this work.
- **Tests.**
  - Core and the store: `core/test/project-links.test.ts`, the store contract cases, and `store-sqlite/test/migrations.test.ts`.
  - Server: `server/test/nextcloud/` (`client` against a fake `fetch`, then `deck`, `wiki` and `bookmarks` against `fake-client.ts`, an in-memory Nextcloud), and `test/routes/nextcloud.test.ts` and `app-nextcloud.test.ts`. The route tests check that the password never comes back out and that the routes are a 404 on the peer listener, and `deck.test.ts` checks that a move that doesn't take is `deck-move-ignored` with no card deleted or created.
  - Web: unit tests beside each file in `web/src/code/` (`DeckTab`, `WikiTab`, `LinksTab`, `openDeckCard`, `startChatFromCard`, `visibleTabs`, `CodePanel`), plus `MarkdownBody`, `AppView` and `NextcloudPanel`.
  - e2e: `packages/web/e2e/nextcloud-tabs.spec.ts` runs against `e2e/fixtures/nextcloud-server.mjs`, a fake Nextcloud on port 4798 (the third `webServer` in `playwright.config.ts`). It checks Basic auth and `OCS-APIRequest`, has a board `E2E Board` with To Do, Doing and Done, the pages `Products/E2E` and `Products/E2E/Notes`, and bookmarks tagged `e2e`, and keeps its state in memory for the run. The spec sets Nextcloud up through Settings and tests it, creates the app through the API, then in the UI moves `#101` from To Do to Doing, marks it Done and finds it under Archived, opens the Notes page and checks its text, and finds the tagged bookmark. `e2e/code-panel.ts` opens a panel tab from the strip or from More tabs, which `code-tab.spec.ts` now uses too, as Files and Terminal no longer fit in the panel's starting width.
