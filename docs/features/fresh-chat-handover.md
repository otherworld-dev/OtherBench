# Fresh chat handover

Spec: `docs/superpowers/specs/2026-11-06-fresh-chat-handover-design.md`. A Claude Code chat that runs for days keeps growing, and every model call reads the whole of it again, which uses up the Claude plan faster and makes each reply slower. When the chat's latest reply read more context per call than a threshold (300k tokens by default), a card under that reply offers to carry on in a fresh chat that starts from a summary the old chat's own session writes. It only asks: nothing moves without a click, and the card never blocks anything, so a chat left running overnight carries on as normal with the card waiting.

- **What is measured.** `SdkEventMapper` keeps the usage of the reply's own agent's last model call (`message.usage` on its `assistant` messages: input plus cache read plus cache written; helpers' calls don't count) and puts it on the `finish` event as `Usage.contextTokens`. The turn total from `result` is the wrong number here, as it sums every call (a long turn can read 60M). `TurnRunner` stores it on the chat as `chat.contextTokens` after each reply that reports it, so every window and paired machine sees it through `chat-updated`. Chats from before this change, and API-model chats, have none and never get the card.
- **When the card shows.** `HandoverCard` (`packages/web/src/components/HandoverCard.tsx`) checks the cheap things first (the chat's `contextTokens`, `suggestsHandover` in `core/src/domain/handover.ts`) and only then looks through the message pool (`handoverTarget` in `web/src/state/handover.ts`). It shows under a finished Claude Code reply with nothing after it, or under a handover summary that failed or was stopped, where it hands over the reply that summary was asked of. It never shows under a summary that finished, or in a compare turn. **Start fresh chat** is disabled, with the reason as its tooltip, while the chat has a reply running, background tasks or waiting notes. **Not now** sets `chat.handoverAskAt` to 1.5 times the current size (300k, then about 450k, then about 675k), and **Don't ask again for this chat** sets `chat.handoverSuggest` to false. The Inspector's Claude Code section has the same switch as a checkbox, "Suggest a fresh chat when this gets big". It doesn't add the chat to Needs you.
- **The handover.** `POST /api/chats/:id/handover` with `{ messageId }` goes to `HandoverService` (`packages/server/src/handover/service.ts`), which answers 202 with the summary turn's ids once that turn has started, and does the rest on the server whether or not a window is open.
  1. It starts a turn under the reply whose user message holds one `{ type: 'handover-request' }` part, on the profile that wrote the reply (its session is the one that holds the chat). `TurnRunner` sends it with `EngineRequest.handover` set and no plan gate, whatever the chat's Plan mode.
  2. The Claude Code engine sends the fixed `HANDOVER_PROMPT` on the continued session and its gate refuses every tool call (`HANDOVER_NO_TOOLS`), so the summary can never stop on a card. With no session to continue it fails with `NOTHING_TO_HAND_OVER`.
  3. Once the summary is complete, a new chat is created titled `<title> (continued)` (then `(continued 2)` and so on). It copies the profile, workspace, extra folders, effort, Claude account and its auto switch, Auto, Plan mode, project, app and `memoryExcluded`. Its first message is an assistant message holding a `{ type: 'handover', direction: 'from' }` link and the summary as text. Claude Code's fresh-session history (`renderHistory`) passes that text on, so no engine change was needed for the new chat to see it.
  4. The summary reply gets a `{ type: 'handover', direction: 'to' }` link. Schedules that targeted the old chat move to the new one (`ScheduleRepo.retarget`), and `chat-handed-over` goes to every window. The window that clicked opens the new chat if it is still showing the old one, and any other window gets a toast that opens it.

  A summary that fails, is stopped, or comes back empty makes nothing, and the card comes back. So does an old chat deleted meanwhile. The request line shows as "Handover to a fresh chat", like `/compact`'s line, and the summary reply can't be regenerated (`HANDOVER_NO_REGENERATE`).
- **Refusals.**
  - 404: an unknown chat or message.
  - 409 `not_here`: a chat that runs on another machine.
  - 409 `busy`: the chat is busy (`chatIsIdle` or `TurnRunner.runningIn`).
  - 409 `handover_running`: a handover is already running for the chat.
  - 409 `not_latest`: the reply isn't the latest. Earlier unfinished handover attempts under it don't count.
  - 400 `not_a_reply`: anything other than a finished Claude Code reply, a compare turn's reply, or a summary that is already handed over.
- **Settings.** `AppSettings.handoverEnabled` (default true) and `handoverThresholdTokens` (default 300,000; the route takes whole numbers from 50,000 to 2,000,000). They are under Settings → Claude accounts → Fresh chats, where the threshold is typed in thousands of tokens. The web reads both through `useFeatures`, and changing them sends `settings-changed`.
- **Storage.** Migration `043-fresh-chat-handover` adds `chat.context_tokens`, `chat.handover_ask_at` and `chat.handover_suggest`, all synced chat fields (`CHAT_FIELDS`). The two new part kinds are left out of search text, the Markdown export renders them as one line each, and stream replay skips them (the link is written after the turn and reaches clients through `messagesChanged`).
- **Limits.** A handover isn't resumed after a restart: its summary reply ends as any reply a restart cuts off, and the card comes back. Chats on another paired machine are refused rather than forwarded. Only Claude Code chats are measured, so API-model chats and compare turns get no card.
