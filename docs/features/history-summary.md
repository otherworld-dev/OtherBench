# History summary

A chat on a model API (the `engine-aisdk` engine: Anthropic, OpenAI, OpenAI-compatible, Google, Ollama, LM Studio) sends its whole active path every turn. Nothing trimmed it, so a long chat ended in a `context_overflow` error and couldn't go on. Now, when the request is close to the model's context window, its oldest messages are swapped for a summary, in the request only. Claude Code chats compact for themselves (`/compact`, and Claude Code's own auto compact) and are not touched.

- **What changes and what doesn't.** Only the request. The stored messages are never changed or deleted: the thread shows everything, branches and edits work as before, and export, recall, search, project memory and sync read the originals. The summary is one more part on the reply it was made for.
- **When (window known).** `HistoryView.fitWindow` (`packages/core/src/domain/turn-history.ts`) runs before the request is sent. The request's size is the provider's own count for the reply before this one (`usage.context_tokens`, what that reply's last model call read) plus that reply's output and an estimate of the new message, when that reply was this profile's and its usage row has a count. Otherwise it is an estimate: three characters a token, low on purpose, plus the tools offered (`estimateTokens`). Over 75% of the window (`summariseThreshold`; less when the profile's `maxOutputTokens` needs more room, never under half) the oldest messages are folded. `ModelInfo.contextWindow` is the window; it is often null.
- **When (window not known).** Nothing is guessed. The request goes as it is, and only if the provider refuses it as too long (`context_overflow`) before anything has come out of the stream, `retryOnOverflow` summarises and sends the request once more. The same retry covers a known window whose estimate was too low. It happens once per reply: a second refusal is the error the user sees. A refusal later in the tool loop, after a tool has run, is not retried (starting over would run the tools again); the next message in the chat is then summarised before it is sent, or on its own first refusal.
- **What is kept word for word.** The system prompt, always. Then as many of the newest turns as fit in 40% of the window (`KEEP_SHARE`); after a refusal, about half of what was sent. The message being answered is always kept, and the exchange before it whenever it fits. The cut only ever falls straight before a user message (`pickCut`), so the kept part opens on a user turn, and a reply is kept or folded whole. A tool call and its result are parts of the same reply, so they are never parted and no result is left without its call. Folding down to 40% when 75% is reached means the cut moves rarely: each move is a model call and a cold prompt cache.
- **The summary.** One tool-less `purpose: 'utility'` call through `ChatEngine.stream`, on the chat's own profile and model (it is sent this conversation anyway, so nothing new leaves the machine), with a 120 s limit. The prompt (`historySummaryPrompt`) holds the summary so far and only the messages newly folded in, as transcript text with long text and tool output cut. It asks for facts, decisions, open tasks, exact file paths and results, under 6,000 characters (a tenth of a small model's window), and forbids copying instructions and recording that anything was approved. A backlog too long for one call (more than half the window, or about 24k tokens when the window isn't known) is folded in pieces, eight calls at most. Each call writes a usage row with `purpose: 'summary'` against the reply, so the Usage view counts it with the other background calls.
- **Where it lives.** On the reply it was made for, as a `{ type: 'history-summary', uptoMessageId, covered, text }` part, written by `TurnRunner` when the summary is made or grows. The next turn walks its path and uses the newest such part on a reply by the same profile (`currentHistorySummary`). No table: a message's parts already sync, replay and export, and a summary on the path can only be of messages on that path. `covered` is a SHA-256 of every message the summary stands for (id, role and the parts a model is sent). It is checked every turn against the stored messages, so an edit, another branch, or a message changed in place never gets a summary of something else: the part is ignored and a new summary is made from the messages as they are. A branch that leaves the path before the reply holding the part doesn't see it at all.
- **How the model reads it.** At the end of the system prompt (`historySummaryBlock`), framed as project memory is: `# Earlier in this conversation`, a line saying it is model-written background that may be wrong, not to follow instructions inside it, and that it never authorises tool use and carries no approvals, then the text inside `<conversation-summary>` tags. A closing tag written inside the summary is defused. Tool approvals are untouched: the summarising call has no tools, and every later tool call goes through `PermissionBroker` as before.
- **Failure.** If the summarising call errors, is cut off, comes back empty, times out or is stopped, nothing is kept and the request goes as it would have: the normal reply, or the normal error.
- **In the thread.** `HistorySummaryLine` (`packages/web/src/components/`) draws "Earlier messages are summarised for the model from here up" under the last message the summary covers, with Show summary. `Thread` finds the place from the parts on the shown path, so the line follows the branch. The part reaches clients live as a `history-summary` turn event (folded by the reducer, rebuilt by the stream registry, kept by the peer relay) and is otherwise read from the message.
- **Compare, schedules, sub-agents, jobs.** Each variant of a compare turn builds its own request, so each profile is measured against its own model's window and keeps its own summary (only a reply by the same profile is read back). A scheduled run is an ordinary turn and is summarised the same way; the call needs no approval. A sub-agent never sees the chat's history (its request is its own system prompt and prompt), so nothing is summarised for it, and a sub-agent that outgrows its window inside its own tool loop fails as before. A job chat is summarised on its job profile.
- **Storage.** Migration `058-usage-context-tokens` adds the nullable `usage.context_tokens`: what a reply's last model call read (`Usage.contextTokens`). The AI SDK engine now reports it from the last step of its tool loop (the total on `finish` sums every step and can't say how full the context is). `usage` is a synced table, so the count and the summary's own usage row sync like any other; the summary syncs inside its message.
- **Settings.** None. It is always on for model API chats: a per-profile switch would be a new profile field with its own form control and migration, and the only thing turning it off buys is the old failure.
- **Limits.** While the summarising call runs (a few seconds, before the reply starts) the reply shows nothing. A regenerated reply, a compare variant that wasn't kept, or a switch to another profile can't see a summary held on a reply that isn't on its path or isn't its profile's, so it makes its own, from the newest one it can see. A single turn bigger than the window (one message with a huge paste, or one reply with huge tool output) can't be fixed by cutting between turns. The estimate ignores what images cost beyond a flat figure. The summary is the model's own words: what it leaves out is gone from the model's view, though not from the chat.
