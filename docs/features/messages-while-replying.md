# Messages sent while a reply runs

Spec: `docs/superpowers/specs/2026-10-18-send-while-replying-design.md` (Deck #946). While a reply is running the composer keeps Send beside Stop, and what you send then is a "note". In a Claude Code chat it goes into the running Claude Code straight away and Claude reads it at its next step, as it does in VS Code. Anywhere else it waits and goes out as the next message when the reply ends. This replaces the old rule that sending was blocked while any reply (a self-started one included) was running.

- **Where it lives.** `NotesService` (`packages/server/src/notes/service.ts`) holds each chat's waiting notes in memory, in send order, and resolves each one exactly once: `folded` into a reply, sent as a `turn`, `returned` to the box, or `removed` by the user (`core/src/types/notes.ts`). Routes are `POST /api/chats/:id/notes` (`{ text, attachments: [{ attachmentId }], parentId, profileIds, clientId }`, 202 `{ note }`) and `DELETE /api/chats/:id/notes/:noteId` (200 `{ note }`, or 409 `{ kind: 'read' }` once Claude has started reading it). A live note no open Claude Code process has any more (`ChatEngine.knowsNote`: not being pushed, queued, starting or read) is given back rather than refused, so a note the engine lost track of can't keep the chat busy. A chat with nothing running answers 409 `{ kind: 'idle' }` and the composer sends a normal turn instead, which covers a reply that ended between the click and the server. While notes are still to go out, `POST /chats/:id/turns`, regenerate and retry answer 409 `{ kind: 'notes-waiting' }`, so nothing jumps them; the composer then sends the box as a note instead. The service finds a chat's running replies through `TurnRunner.runningIn`, which keeps them by chat, rather than scanning every streaming message.
- **Which path a note takes.** It goes in `live` only when the composer is pointed at the one running reply: `parentId` is that reply and the only profile picked is the reply's own, the reply isn't a scheduled run's or a /compact's, no `wait` note is already queued, and the engine can take it (`ChatEngine.sendToReply`). Anything else takes the `wait` path with the composer's parent and profiles, so a note never lands in a reply you aren't looking at or goes to a model you didn't pick. A live note the engine refuses falls back to waiting. The parent is settled on the server first: when notes have already gone out as a turn or follow-on under the parent the composer sent (it hadn't shown them yet), the note goes on from the tail of their branch, so it doesn't start a branch beside them (`NotesService.caughtUp`, from the chat's last 20 deliveries). If that tail is the running reply and the profile is its own, the note goes into it live, as it would have once the composer caught up. An unresolved compare turn there leaves the parent as sent.
- **Live path (Claude Code).** `ClaudeCodeChatEngine.sendToReply` pushes the note into the reply's live process as a user message whose `uuid` is the note's id, with its images as image blocks (a file, or an image over the cap, becomes a line saying it wasn't sent). While it reads the images the note is pending (`pendingNotes`): `knowsNote` counts it, and a Take back meanwhile withdraws it, so it is never pushed after being marked removed. Claude Code never echoes the text back, so where it landed is read from its `command_lifecycle` frames, which `LiveProcess.pump` tracks in `live.notes`:
  - `queued`: Claude Code has it and hasn't read it. The note shows as waiting ("Waiting for Claude to finish its current step").
  - `started` while the reply is still attached: Claude read it mid-reply. The pump puts a `NOTE_PICKED` marker in the reply's feed, the engine emits `note-picked`, and `TurnRunner` swaps that for a `user-note` part (`NotesService.take`) at that point in the reply's parts and on the stream. The answer follows in the same reply.
  - `started` after the reply's own `result`: Claude Code is running it as a turn of its own. The note goes into `live.starting`, and the next main-agent frame starts a follow-on (`handleIdle` → `selfStart` with `noteIds`, `NotesService.followOn`, `TurnRunner.runFollowOn`): a normal user message under the reply holding the note(s) in order, a reply under it streaming that turn, and the head moved to the new user message. A follow-on is never treated as a self-started reply (no notice, always attended). Several notes Claude Code batches into one turn become one user message.
  - `cancelled` or `completed`: tracking ends. A note that had started but whose turn ended before showing anything (an early error) is reported back (`notes-dropped`) and returned to the box. So is a queued note Claude Code cancels or completes without being asked; a cancel the engine asked for (Take back, Stop, a failed reply) isn't reported, as whoever asked accounts for it (`LiveProcess.cancelling`).
  - A note picked in a turn nobody shows (a self-start the server declined, or the rest of a stopped turn read in the background) is reported dropped too (`readUnshown`), so it comes back rather than waiting for good.
- **Wait path.** The note sits on the server and shows at the end of the thread ("Sends when the reply finishes"). When every reply it waited on ends `complete` (all variants, for a compare turn) the waiting notes go out as one turn, a single user message in send order, with the first note's parent and profiles. If earlier notes went out as a turn or follow-on under that parent after the first note was sent (the composer hadn't shown them yet), the turn goes on from the tail of their branch instead of forking beside it; an unresolved compare turn there leaves it on its parent. If any reply in the chat ended cancelled or with an error while they waited, they all come back to the box instead, never sent, once nothing in the chat is streaming: one failed compare variant doesn't take them out of view while the other is still running.
- **Untyped SDK calls.** SDK 0.3.287 doesn't type any of this, so it goes through a narrow widening of `QueryFn` (`engine.ts`) and `LiveQuery` (`live.ts`), documented where they're declared. `cancelAsyncMessage(uuid)` drops one queued message and resolves true, or false once it has started. `command_lifecycle` frames (`lifecycleOf`) and `system/init.capabilities` (`LiveProcess.capabilities`) are read off the raw messages. A process whose init doesn't list `msg_lifecycle_v1` gets no live notes: they take the wait path.
- **Stop.** Stop cancels the reply's own queued notes one by one with `cancelAsyncMessage` and then calls a plain `interrupt()` (`stopTurn`). It deliberately doesn't use `interrupt({ cancelQueued: true })`, the spec's original plan, because that also drops a background helper's queued `task_notification`, and the helper's report would be lost. The stopped reply's notes come back to the box with their text and attachments, after whatever is already typed. A reply that fails, or whose process closes, with notes still queued does the same (`cancelNotes`, `onClosed` → `notes-dropped`). Either way the composer shows "Not sent: the reply ended before it was read. It's back in the box."
- **Attachments.** A note's attachments stay unsent until it is delivered, as a binding is only set once. While it waits they are held (`heldAttachmentIds`): left out of the chat's attachment list, refused for another note, and `DELETE /attachments/:id` answers 409. The reply a live note goes into may still load their images (`TurnRunner`'s `heldAttachment`, same chat and cap). They are bound to the reply that read the note, or to the user message a turn or follow-on makes.
- **The stream.** The chat's stream carries `{ type: 'notes', notes }` (the whole waiting set) and `{ type: 'note-resolved', noteId, outcome, clientId, note? }` (`note` only for `returned`), and its `hello` has `notes` and each chat's last 200 `noteOutcomes` (a count, not a time, so a tab away for long still learns what became of its notes), so a reload neither loses nor repeats one. A hello can arrive before the chat's messages have loaded; this tab's notes it finds lost are then held (`unsureNotes`) until the load ends (`settleUnsureNotes`), so one a reply shows as read isn't put back as "Not sent". A folded note is a `user-note` reply event, stored in the reply's parts, so a reload, another tab, a paired machine and the synced copy all show it in the same place.
- **Composer.** Send and Stop sit side by side while a reply runs (or notes wait), Enter sends, and the box clears as usual. Waiting notes show at the end of the thread, styled as yours and faded (muted text and a dashed border, not opacity, which took the muted text below AA contrast in both themes), with **Take back** (`components/WaitingNotes.tsx`), which returns the text and attachment chips to this tab's box, or does nothing if Claude has already started reading it. Only the tab that sent a note (its `clientId`, `lib/clientId.ts`) gets it back. That tab also keeps a copy until it's resolved (`sentNotes`), and if the server no longer knows it (a restart, a dropped peer) it goes back into the box with the same line, unless a loaded reply shows it as a `user-note` part (it was read). The client id and the copies are kept in `sessionStorage` (`otherbench.clientId`, `otherbench.sentNotes`), so a reload of the tab keeps both: a note sent before the reload still comes back after it, and exactly once. A duplicated tab copies that storage, so the id is also marked held (`otherbench.clientIdLive`) while a page of the tab shows, and let go on `pagehide`: a reload lets it go before the new page reads it and keeps it, while a copy finds it still held by the tab it came from, makes its own id and drops the copies of that tab's notes. Every read and write is guarded; with storage blocked they last one page load, as before. A chip a returned note brings back gets its size from the chat's attachment list. Commands (/clear, /compact and Claude Code's own) can't be sent mid-reply: the composer says "Wait for the reply to finish, or stop it, before sending a command." The server is the authority and refuses the same way: /clear and /compact, and for a Claude Code profile any `/name` its Claude Code lists (`isCommandText` in `core/src/domain/context-lines.ts`, shared with the composer; the list is asked for only when the text starts with `/`). So the composer refuses the same whether or not it had loaded the list.
- **History.** A `user-note` part is the user's words wherever a reply is replayed. Claude Code's rebuilt history renders it as a `[user]` line where it falls (`history.ts`). For API profiles `toModelMessages` splits the reply at the note into assistant / user / assistant (`engine-aisdk/src/convert.ts`). Retry, regenerate and edit rebuild a reply from its user message as before, so notes folded into the old attempt aren't carried over, and that attempt keeps them as a variant.
- **Elsewhere.** Scheduled runs wait for a chat's notes to go out first (`hasWaitingNotes`), and a note sent during a scheduled run's reply takes the wait path and goes out attended. On a paired machine both note routes are forwarded to the machine running the chat (the POST syncs first, so it has the attachments), and `user-note` events are relayed in place (`peer/forward.ts`).
- **Tests.** `server/test/notes/service.test.ts`, `server/test/routes/notes.test.ts`, `engine-claude-code/test/engine.test.ts` and `live.test.ts` (the fake live query folds, runs late notes as their own turn, batches, emits `command_lifecycle` and honours `cancelAsyncMessage`), `core/test/turn.test.ts`, `web/src/state/notesReload.test.ts` (a reload or a duplicate of the tab, by evaluating the modules afresh over the same `sessionStorage`), `web/src/state/useChatSync.test.tsx` (a hello before the messages), and `web/e2e/send-while-replying.spec.ts` for the wait path in a browser.
- **Live check (2026-10-18, Claude Code on the Claude login, haiku).** Driven through the HTTP API and the chat stream against a separate server and data folder. All of these behaved as intended:
  1. "what is 17 + 25?" sent during the first of three `sleep 6` Bash calls showed as waiting, became a `user-note` part straight after the first tool result, and the reply went on "17 + 25 = **42**. Now running the second command".
  2. A note sent while the final answer was being written wasn't folded. After the reply finished it became a user message under it with its own reply ("6 × 7 = 42"), and the head moved to that user message.
  3. A note then Stop: the reply was cancelled and the note came back (`returned`, with its text). Nothing ran it afterwards, and the next message in that chat got a normal answer.
  4. A note with a PNG (red left half, blue right half) was folded mid-reply and Claude described "red on the left half and blue on the right half". The attachment was bound to the reply.
  5. Take back during a Bash call removed the note (`removed`), and the reply finished without it.
- **Known limits.**
  - A note Claude Code starts at the instant of Stop may already have been read, even though it comes back to the box.
  - When Claude Code batches several notes into one turn and its frames name only some of them, the others may be reported dropped and come back, although Claude read them.
  - A started note whose turn never emits anything keeps its process busy (`inTurn`) until the process closes, so the next message in that chat waits.
  - Notes sent from a paired machine that become a turn there aren't kept on the sending machine if the peer drops: the sending tab's copy is all that's left.
  - When Claude Code can't list its commands within 3 seconds, a `/name` note other than /clear or /compact goes through as text, as the composer's menu then offers only those two.
  - Waiting notes are in memory only and don't survive a server restart; the sending tab puts them back in the box.
  - A tab restored after the browser crashed (no `pagehide`) looks like a copy: it gets a new client id and drops its note copies, so a note it sent before the crash doesn't come back to it.
  - A lost note is recognised as read only when a reply shows it as a `user-note` part; one that became a turn or follow-on carries no note id, so with its outcome gone (over 200 later outcomes in the chat, or a server restart) it could come back although it was sent.
  - No "send now" that interrupts the step Claude is in (`priority: 'now'`), and a waiting note can't be edited in place: take it back, change it and send it again.
