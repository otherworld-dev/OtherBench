# Chats that message each other

Spec: `docs/superpowers/specs/2026-11-06-chat-to-chat-design.md`, and for paired machines `docs/superpowers/specs/2026-11-13-chat-sends-across-machines-design.md`. A chat's model can send work to other chats, on this machine or a paired one, for example the chat for another app whose code also needs changing. The chats it sends to start on it by themselves, and when every one has finished, their replies come back to the sender as one message that starts its next reply. This replaces copying requests and answers between chats by hand.

- **The tool.** `message_chats` (`packages/core/src/domain/chat-sends.ts` for the rules and text, `packages/tools/src/chats-tool.ts` for the spec). `list` shows the chats it can send to and the apps it can start a chat in, by their exact names, each with the machine it runs on and whether that machine takes sends (`acceptsSends`: null when it hasn't said or is off); `send` takes up to 4 messages, each to an existing chat (`chatId`) or to a new chat in an app (`app`, by name). API profiles get it from `listTools`; Claude Code gets it relayed (`relayOtherBenchTools`), so it runs only arguments an approval stands behind. A profile switch, Settings > Profiles > "Message other chats" (`toolPolicy.chatMessages`, absent = on), turns it off.
- **Asked once per chat.** Source `'chats'` takes no shortcut in the broker (`permissions/sources.ts`): the first call in a chat raises a card, and "Allow for this chat" covers the rest of that chat. The card has no "Always", and an "always" answer that arrives anyway is stored as the chat's grant (`grant-minting.ts`). It asks in Auto mode too: the provider's Auto branch, which approves OtherBench's own tools without a card, skips source `'chats'` (`provider.ts` `requestApproval`), because text planted in one chat could otherwise set other chats working unasked. Never offered to, or allowed from, a sub-agent, a Claude Code helper, a scheduled run or a compare turn.
- **Where it runs.** `packages/server/src/chat-sends/service.ts` (`ChatSendService`), built in `container.ts` after the notes service. Each send is a row in `chat_send` (migration 044, local, no sync triggers, no foreign keys): `queued`, `running`, then `replied`, `failed`, `stopped` or `dropped`.
- **Delivery.** A target chat gets the message as a new turn, a user message with a `chat-link` part (`kind: 'from'`) and a text part that says which chat sent it, that its agent (not the user) wrote it, and that the final reply goes back. Engines drop `chat-link`; the model reads the text. A busy chat (a reply running, or the user's own messages waiting to go out) gets it when it is free, one message at a time, oldest first. A new chat in an app takes the app's folder and default profile, starts with Auto on, is titled from the message's first line, and opens the app in the Code sidebar (`createAppChat`, routes/chats.ts).
- **Coming back.** A reply that sent work waits. When every send of that reply has settled, the sender's chat gets a user message with a `chat-link` part (`kind: 'replies'`) and the replies (`repliesText`, each cut at 20,000 characters) and starts its next reply, as the profile that sent them, from the end of its thread. If the sender is busy it waits for that reply to end. A target that sends work on itself counts as finished only when its own replies came back and it ended a reply without sending more: the sender gets that last reply, not "I've asked C". The rows a reply works on move to its resumed reply (`toReplyId`).
- **Across machines.** A chat or app on a paired machine can be sent to; the work runs on the machine the target runs on. A new chat in an app runs on the machine its folder is bound to (`appMachine`: a location's goes to this machine if it resolves here, else the first paired machine where it does). The sender's machine keeps its row with `toNode` and hands the send over (`chat-sends/remote.ts`, `POST /chats/:chatId/sends/incoming` on the other machine's peer listener, after asking it to pull first); that machine keeps a mirror row under the same id with `fromNode`, delivers it as above, and reports how it ended (`POST /chats/:fromChatId/sends/:id/outcome` here) instead of resuming anything there. A handover, report or stop that doesn't get through is tried again on every tick (`remoteWork`, migration 049) until taken. The chain's depth travels with the send, and its count as `chainBase`. Delivered and resumed turns hold the other machine's `PeerInfluence` mark while they start (`markPeerTurn`).
- **The setting.** Settings → Machines, "Let chats on paired machines send work to chats here" (`peerChatSends`), off by default, only changeable on that machine. Each machine tells its peers in its activity announcement (`acceptsChatSends`), so `list` and a send refuse a machine that said no, naming the setting. An outcome needs no setting: it can only settle a send this machine made, to that same machine, and its path's chat must be the send's own.
- **A machine that is off.** A send to a machine that isn't reachable, or is refusing for a while (computer use in control there), isn't refused: it is held (`heldReason`), the model is told the user has been asked and to end its turn, and the user gets a desktop notification (`chat-send-held`, under the approvals switch) and the status word "Machine off" in Needs you, on either machine. The send card offers **Run here** (only when its chat has no folder or its folder is on this machine; it moves the chat here, or makes the new app chat here), **Wait** (the default: it goes when the machine is back; this just stops it needing the user) and **Cancel** (`cancelled`: the sender carries on without it). A machine on an older build fails the send at once ("needs updating"). Run here is refused on the peer listener (it would start a turn in a chat the call doesn't name); the card's other calls are forwarded to the machine the chat runs on, so they work from either.
- **Limits.** A chain (everything that follows from one message the user sent) is at most 3 chats deep, at most 4 sends per reply and at most 10 in all; past a limit the tool tells the model to stop and ask the user. A chat can't send to itself or to a chat waiting in the same chain. Only chats that aren't archived, and run on this machine or a paired one, can be sent to.
- **Stop.** The send card's Stop (`POST /api/chats/:id/sends/stop`, forwarded to the machine the chat runs on; the older `POST /api/chat-sends/:messageId/stop` still works here) stops everything that reply started, down the chain and across machines (the other machine is told until it takes it, and its Stop passes even while computer use may be in control there), and the sender doesn't carry on. A held send that was handed over once with no answer back is stopped there too, on Stop or Cancel, since that machine may have it; Run here isn't offered for one. Stop on the sender's own reply while it runs does the same. Stopping a target in its own chat is that target's answer ("stopped"), and the sender carries on with it; so is the Stop on a target's own send card, for the chats above it.
- **Dropped.** A /clear or /compact in the sender after it sent, or the sender deleted, closes the group without a turn (`resumedAs: 'none'`); whatever that reply was doing for a chat above it ends `dropped`.
- **Restarts.** At start-up a running send whose reply isn't running any more ends as that reply is stored (a restart has already reconciled it as an error), and queued sends get another look.
- **The UI.** `ChatSendCard` under the reply that sent (one row per chat: its title, app, status and a link), `ChatLinkBadge` over the generated user messages ("From …", "Replies from …"), and the status word "Waiting on chats" while a chat's sends are out (`waitingOnChats`, from `GET /api/chat-sends/waiting`; not Needs you). The card re-reads `GET /api/chats/:id/sends` on every `chat-sends-changed` app event.
- **Mock.** `#send <chatId | app:Name> <text>` makes one send through the real tool and ends with "Sent." (`packages/web/e2e/chat-to-chat.spec.ts`).
- **Tests.** `core/test/chat-sends.test.ts`, `core/test/permissions-chats.test.ts`, the store contract's "chat sends", `tools/test/chats-tool.test.ts`, `server/test/chat-sends/` (`service.test.ts`; across machines `service-sender`, `service-target`, `service-link` (two services wired together), `remote` and `peer-routes`), `server/test/peer/chat-sends.test.ts` (two real servers paired), `server/test/routes/chat-sends.test.ts`, the web component tests and the e2e above.
- **Known limits.**
  - The sends aren't synced: each machine keeps its own side of one that crosses machines.
  - Across machines, the chain limits are counted from what each side knows: sends a target makes after its handover aren't counted on the sender's machine, and "a chat waiting in the same chain" only sees this machine's rows.
  - A send can wait on a machine that never comes back until it is cancelled (held) or stopped (handed over); there is no time limit. Nothing asks the other machine about a send it took: if that machine loses its copy, the send stays "Working" until Stop.
  - A group that had fully come back but not yet resumed its sender when the server stopped isn't found again at start-up; that sender stays quiet.
  - The delivered and replies messages show the whole text the model read, header included, under their badge.
