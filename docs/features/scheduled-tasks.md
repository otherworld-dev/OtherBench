# Scheduled tasks

Spec: `docs/superpowers/specs/2026-10-12-scheduled-tasks-design.md` (Deck #925). A schedule runs a prompt on a profile daily, on chosen weekdays, monthly, every few hours or on a cron rule, in the zone of the machine it was made on. It either adds a reply to a fixed chat or starts a new chat in a project (`<name> · 12 Oct 2026`, never auto-titled). The clock button in the sidebar footer opens the Scheduled overlay. "Schedule…" in a chat's or a project's menu opens the editor on that target.

- **Where it lives.** `schedule` and `schedule_run` (migration `023-schedules`) are local. They have no sync triggers, so a schedule runs only on the machine that holds it. A paired machine sees it, reads its history, and can manage it only if that machine allows it (see "Across machines" below). Deleting its chat, project or profile deletes it. Archiving its profile leaves it, and its runs record "Didn't run" until the profile is changed.
- **Rules.** `ScheduleRule` in `packages/core/src/domain/schedule.ts`, stored as JSON in `schedule.rule`, so the two later kinds needed no migration (an older build reads one as an unreadable rule, and the schedule shows disabled). `hourly` runs at its start time and every 1-23 hours after it until midnight, starting again from the start time each day, on every day or only on chosen weekdays (every 3 hours from 08:00 is 08:00, 11:00 … 23:00). `cron` is a standard five-field rule, parsed by hand in `packages/core/src/domain/cron.ts` (no dependency): `*`, lists, ranges, steps, month and weekday names, 7 for Sunday, and `@hourly`, `@daily`, `@midnight`, `@weekly`, `@monthly`, `@yearly`, `@annually`. No seconds field and no `@reboot`. Day of month and day of week follow Vixie cron: if neither field starts with `*`, either matching is enough; if one does (`*` or `*/2`), both must match. A day of month past a month's end never matches that month, unlike the monthly kind. A rule that can never run (`0 0 30 2 *`) is refused. Create and PATCH check the rule with `parseRule` and answer 400 with a plain message (`"rule.cron": The minute field's "61" is out of range: 0 to 59.`). Every kind goes through the same `nextRunAt` walk and `wallToInstant`, so clock changes behave alike: a slot in the spring gap moves forward by the gap, one in the autumn fold runs once at the first time, and two slots that land on the same instant run once. A day with no clock change near it takes a fast path, so `* * * * *` stays cheap. The walk looks up to 50 years ahead, for rules such as 29 February on a Monday.
- **When it runs.** `ScheduleService` (`packages/server/src/schedule/service.ts`) re-arms one timer for the earliest next run, never more than 30 s away, so sleep and clock changes are caught within 30 s. A schedule that missed slots runs once, marked late if more than 5 minutes past due. At most two scheduled runs go at once. A busy target chat makes its schedule wait, and a schedule still running at its next slot records that slot as "Didn't run". On start, a run left running by the previous process is marked as an error ("OtherBench stopped before this run finished."): its reply was already reconciled, so there is nothing left to time. `nextRunAt` moves before a run starts, so a crash never repeats a slot.
- **Time limit.** Each schedule has one (`Schedule.timeLimitMinutes`, migration 038, `schedule.time_limit_minutes`): 1 minute to 24 hours, or null for no limit. A new schedule gets 30 minutes (`DEFAULT_SCHEDULE_TIME_LIMIT_MINUTES`), and so did every schedule made before, since 30 minutes was the fixed limit all runs had: long enough for a report or a triage run, Claude Code's included, short enough that a run stuck in auto mode doesn't go all night holding one of the two run slots. The editor's Time limit offers 10 and 30 minutes, 1, 2, 4 and 8 hours and No limit (`SCHEDULE_TIME_LIMIT_CHOICES`), plus a schedule's own value if it was set to something else through the API; the list shows "No time limit" or "Time limit 2 hours" when it isn't the usual 30. The service arms a timer when the run's reply starts (`track`), so everything after that counts, a wait on a card, a sub-agent or a long command included; with no limit no timer is armed. A run keeps the limit it started with if the schedule is edited during it. At the limit the reply is stopped through `TurnRunner.cancel`, the same abort the user's Stop uses, which settles a card it waits on, stops its sub-agents, kills a shell command's process tree and ends Claude Code's process. `cancel` takes an optional notice for this: the stopped reply ends with a notice part, "Stopped at the schedule's time limit of 30 minutes.", which is kept with the message and sent live before its status, so the run's chat says why it stopped. The run is recorded as "Timed out" with the same text as its detail (whether the engine ended the reply cleanly or with an error the stop caused), and `schedule-run-finished` goes out with `timed_out`: the desktop and browser notifications say "Timed out. Stopped at the schedule's time limit of 30 minutes." The run's opening paragraph tells the model the limit ("It is stopped if it is still going after 30 minutes."). A Stop by hand before the limit is still "Stopped", with no notice.
- **Unattended.** Every scheduled run (and Run now) is unattended: `TurnInput.unattended` → `EngineRequest.unattended` → `ToolContext.unattended`. The last two came from thread cards and nothing set them until now. The schedule service sets them, and `TurnInput.unattended` is new. `OtherBenchToolProvider.settle` refuses any call that would raise a card with `approval_unavailable`, audited `deny:unattended` (the Inspector says "refused: nobody to approve (scheduled run)"), and the run's history counts them. Grants, read-only tools under "Ask on changes", artifacts and allowed web tools still run. Thread cards already answer for the model in an unattended run: a question gets the unattended text and a plan stays closed. Claude Code's auto mode is used in a scheduled run only when its schedule opts in (`Schedule.autoMode`, migration 035, on a Claude Code profile): `TurnInput.unattendedAuto` → `EngineRequest.autoMode` → `ToolContext.unattendedAuto`, which is what lets the provider take a `deferAsk` in an unattended run. The chat's own Auto never applies to a scheduled run, its helpers between replies or a self-start (`SelfStart.unattendedAuto`). The flag is only ever set by the service, never from a request body, so the peer listener can't set it.
- **Sandbox.** Sandboxed commands run unattended under "Ask on changes" (no card). `unattendedWarnings` reads `ToolPolicy.shellRuns` through `runsShellInSandbox`: only a shell on this machine gets the "needs approval" line, and a sandboxed one gets a line saying hosts off its list are refused unless a grant already covers them (an Always grant, or one for the schedule's own chat).
- **Editor.** Repeats offers Daily, Weekly, Monthly, Every few hours and Cron rule. Under the rule it lists the next three runs in the schedule's zone (`previewRuns` in `web/src/views/schedules/draft.ts`), or what is wrong with the rule as it is typed, so a typo in a cron rule shows at once. A new schedule's preview uses the browser's zone, which is the server's while schedules run on the machine that holds them.
- **Deleting a chat or project.** Its delete dialog says how many schedules go with it ("Its 2 schedules are deleted too."), and nothing when there are none. The count is read from `/api/schedules` when the dialog opens (`useScheduleCount`); if that fails the line is left out. A project's line counts its own schedules only, as its sub-projects and chats stay.
- **Notifications.** In the desktop app, shown even while OtherBench is focused (Settings → Desktop → "Scheduled runs"). The run's own "Reply finished" is suppressed. In a plain browser, Settings → Notifications → "Scheduled runs" turns on browser notifications for a run finishing, failing or not running (`web/src/lib/browserNotify.ts`). It is off until turned on, and the browser asks first. A notification is tagged with its run, so several open tabs show it once, and a click opens the run's chat. They only appear while OtherBench is open in a tab, and only where the browser offers the Notification API (`http://127.0.0.1`, `localhost` or https; not plain http to another address, and not Chrome on Android, which needs a service worker). Replies and approvals still don't notify in a browser.
- **API.** `/api/schedules` (list, create, PATCH, DELETE, `/:id/runs`, `/:id/run` → 409 `{ kind: 'running' | 'busy' | 'full' }`). Create and PATCH take `timeLimitMinutes` (whole minutes, 1 to 1440, or null; left out on create it is 30), checked by `parseTimeLimit`. On the peer listener only through `peerScheduleRoutes` (see "Across machines").
- **Across machines.** The Scheduled overlay lists each paired machine's schedules below this machine's, under "On PC · runs there". A row shows what a local row does: name, Paused, Running, the rule in words, the target chat or project and the profile by name, auto mode, the time limit if not 30 minutes, the next run in its zone and the last run's result and time, with Open for that run's chat once it has synced here. A chat, project or profile not synced here yet is named "a chat not on this machine yet" and so on. How it gets here: the machine holding the schedules sends a `schedules` announcement on its `/peer/events` stream (`PeerService.schedulesAnnouncement`, built by `ownSchedules` in `server/src/peer/schedules.ts`), straight after `activity` when the stream opens, and again whenever it differs from the last one sent (`announceSchedulesIfChanged`, checked on `schedules-changed`, `schedule-run-started`, `schedule-run-finished`, `chat-deleted`, `sync-applied`, `settings-changed` and after the syncer announces local changes, which catches a project or profile deleted with its schedules). It is a separate event rather than part of `activity` because `activity` goes out on every reply and card. Besides the rows it says whether the machine lets paired machines manage its schedules (`manage`) and the zone it makes schedules in (`timezone`); an older build sends only the rows, read as not managed. The receiving server checks and bounds every field (`peerSchedulesOf`, `peerScheduleControlOf`), keeps them per machine and emits `peer-schedules`; `GET /api/peers/schedules` (this machine's own `/api`, not the peer listener) gives each paired machine's status, `manage`, zone and list, named from this machine's synced chats, projects and profiles (`namedPeerSchedules`). While a machine isn't reachable the route gives no rows and not managed, and the section says "PC isn't reachable, so its schedules can't be shown. They still run there." A machine that never sends the announcement reads as not sharing them, and the section says to update it. The web (`views/schedules/PeerSchedules.tsx`) re-reads on `peer-schedules`, `peer-status`, `peers-changed`, a sync and every `/api/events` hello (`peerSchedulesVersion`), and with the overlay's own 30 s re-read. Nothing is shown when no machine is paired. Schedules still don't sync: each stays on, and runs on, the machine that holds it.
  - **History** is on every row. It reads the runs from the machine that holds the schedule (`GET /api/peers/:id/schedules/:sid/runs` here, which calls `GET /api/schedules/:sid/runs` on that machine's peer listener) and shows the same list as a local schedule's History (`views/schedules/ScheduleHistory.tsx`, shared by both), with Open only for a run whose chat has synced here. It is a read, like the announcement, so it needs no opt-in; the runs' chats reach this machine by sync anyway.
  - **Managing them** (Run now, Pause/Resume, Edit, Delete… and "New schedule on PC") is offered only while that machine says it allows it. Settings → Machines → "Let paired machines manage this machine's schedules" (`AppSettings.peerScheduleControl`) is set on the machine that holds the schedules, is off by default, and is machine-local like every setting (the `app_setting` table has no sync triggers, and the peer listener has no settings route, so a paired machine can't turn it on). It is a plain checkbox, not the native confirm computer use's switch needs. While it is off, the rows keep the line "These run on PC and can only be changed there". While it is on, this machine's UI sends each action to `/api/peers/:id/schedules…` here (`routes/peers.ts`), which calls that machine's peer listener; a create or edit has that machine pull from this one first (`/peer/sync-request`), so a chat, project or profile just made here is there to check. On that machine `peerScheduleRoutes` (`server/src/peer/schedule-control.ts`, mounted inside `forwardedApi`) allows exactly `GET /schedules` (the full list, prompts included, read when Edit is pressed), `POST /schedules`, `PATCH /schedules/:id`, `DELETE /schedules/:id`, `POST /schedules/:id/run` and `GET /schedules/:id/runs`; any other path or method under `/schedules` is a 404, so a route added to `/api/schedules` later is never reachable from a paired machine by accident. The handlers are `/api/schedules`'s own (`schedulesRoutes`), so the checks and the answers are the same as from that machine's own UI: the rule, the time limit, a profile that isn't archived, a target chat that runs on that machine ("This chat runs on Laptop…"), and the zone always that machine's, never the body's. The editor (`ScheduleEditor` with `machine`) says "on PC", offers only chats that run there and shows that machine's zone. The setting is read on every call, so turning it off stops the next call: the management calls then answer 404 as they did before these routes existed, with `kind: 'peer_schedules_off'` and a reason that names both machines, which the row shows. Stop for a running scheduled run isn't offered from the other machine; the run's chat shows live there and has its own Stop.
  - **Every change is recorded with the machine it came from.** After a create, edit, pause, resume, delete or Run now succeeds, the holding machine writes a row to `schedule_peer_change` (migration 045, local, no sync triggers, no foreign key so a delete is recorded too): the schedule's id and name, what was done, the caller's authenticated node id (never something it sent) and, for Run now, the run's id; and logs a line naming the machine. An edit is read from what the PATCH actually changed (name, prompt, profile, rule, auto mode or time limit), not from what was sent, and wins over a pause in the same call; a call that changed nothing records nothing. Creates, edits and deletes are only dropped once 90 days old; pauses, resumes and Run nows are trimmed per schedule to the newest 20, always keeping the newest of each, so a paired machine can't push the record of an edit out by flooding cheap calls. A local row shows the newest one ("Paused from Laptop, 2 min ago", `ScheduleView.changedFrom`).
  - A change from a paired machine doesn't mark the chat as that machine's for computer use (`PeerInfluence`), unlike a turn: a scheduled run is unattended and computer use refuses unattended runs, so there is nothing for the mark to guard. The schedule routes sit behind the listener's desktop-only gate, so while computer use may be in control of that machine (and it doesn't let paired machines drive computer use) a schedule change from a paired machine is refused like any other write.
  - Tests: `server/test/peer/schedules.test.ts` (two peer services, then two real servers over TLS: a schedule made, edited, run, deleted, and deleted with its chat or project on the PC shows on the laptop; unreachable gives no rows; the prompt never crosses while managing is off; with it off every schedule path but the history is refused and the PC's store is unchanged, with computer control on or off; the history reads the PC's list; with it on the laptop pauses, resumes, edits, runs, makes and deletes one, gets the PC's own validation answers and each change is recorded with the laptop; a flood of pauses after an edit leaves the edit on record; turning it off refuses the next call), `routes/settings.test.ts`, the store contract's peer-change tests, and the "paired machine's schedules" block in `web/src/views/SchedulesView.test.tsx`.
- **Tests.** `packages/web/e2e/schedules.spec.ts` makes a chat schedule from the chat menu and a project schedule from the project menu, runs both with Run now, checks a refused `#recall` call shows no card, and pauses and resumes a schedule. The chat schedule is given a 1 hour time limit in the editor, and the spec checks the list and the run's opening paragraph say so. A run actually timing out is covered by the service's unit tests (fake clock), not e2e. Every schedule is set for twelve hours ahead so nothing fires on its own.
