# Code terminal

Spec: `docs/superpowers/specs/2026-10-21-code-terminal-design.md`. Code mode's right panel has a **Terminal** tab: real shells in a PTY, several per app, opened in the app's folder and shown with xterm.js. It replaces the old Inspector **Open terminal** button and the desktop's `open_terminal` command, which are gone. Chat mode has no terminal. The right panel's width can be dragged on its left edge (`otherbench.codePanelWidth`: 24rem to start, 18rem at least, at most 70% of the window). It never squeezes the chat panes below 20rem beside the sidebar (`CHAT_AREA_MIN_REM` in `state/codePanelWidth.ts`). The column's CSS width applies that cap (`CODE_PANEL_CSS_WIDTH`), so a window resize or a sidebar drag narrows the panel at once. The saved width is kept and comes back when there's room.

- **Server.** `packages/server/src/terminal/`:
  - `manager.ts` holds `TerminalManager`. It keys terminals by app, keeps the last ~1 MB of output per terminal. It trims only once the buffer is a quarter over, so heavy output doesn't copy the whole buffer for every chunk. A trim starts at a line start, so a replay never opens inside an escape sequence, and otherwise never on the second half of a surrogate pair, and emits `terminals-changed` on `/api/events` for every create, rename, exit, restart and kill. It allows 10 terminals per app and 30 in all, with no idle timeout. It knows nothing of HTTP, so a paired machine's forwarding can call the same methods later.
  - `node-pty.ts` loads `@lydell/node-pty` (node-pty with prebuilt N-API binaries, pinned 1.1.0) lazily. On Windows it also loads `conpty.node` there and then, because the package imports without it. If either fails, terminals are off (`no-pty`) and nothing else is affected. On Windows a PTY is closed through node-pty 1.1.0's internals, which close the pseudoconsole and its `conhost.exe`, and not through `kill()`. Once the shell is gone, `kill()`'s console-list helper prints "AttachConsole failed" and waits 5 s. If the internals change in an upgrade, it falls back to `kill()`. Every PTY is closed when its shell exits or is killed: a ConPTY left open keeps a `conhost.exe` running.
  - `shells.ts` finds the shells. On Windows these are PowerShell 7 (the default when installed), Windows PowerShell, Command Prompt, Git Bash (beside `git`) and WSL. On POSIX they are `$SHELL`, bash, zsh and sh. Only absolute paths count. Windows' own shells come from System32 before PATH, and a `where` match in the server's own working folder is refused. They are looked for once, on the first status call or new terminal, without blocking the server: the `where` runs (System32's `where.exe`) are asynchronous, side by side, and skipped for a shell System32 already has. The client picks a shell by id, never by path, and the arguments are fixed per shell.
  - `kill-tree.ts` ends a shell and everything it started. On Windows that is `taskkill /T /F` from System32. On Linux and macOS node-pty starts the shell as a session leader, so everything it starts is in its session, background jobs included (bash and zsh give each its own process group, which the old group kill missed). Closing a terminal sends SIGHUP and SIGCONT to every process in the session (`pgrep -s`) and to their descendants that left it with setsid (`ps -A -o pid=,ppid=`), as a terminal hanging up does, then SIGKILL to anything still there a second later (nohup). Process ids are parsed strictly, and the server, what started it, and PIDs 0 and 1 are never signalled: a blank line in pgrep's answer once read as PID 0, and walking from it reached every process. More than 500 found means the listing is wrong, and only the shell is killed. A program that daemonised away from both the session and its parent isn't found, as no real hangup reaches it either. This is covered by unit tests with a faked process table only: it hasn't been run on Linux or macOS.
  - `routes/terminals.ts`: `GET /api/terminal/status`, and `/api/apps/:id/terminals` (list, create, PATCH name, DELETE), `/:tid/input` (64 KiB at most), `/:tid/resize`, `/:tid/restart`, `/:tid/stream` and `/:tid/output?from=`. The stream sends a named `hello` with the buffer, then unnamed `{ type: 'output' | 'exit' }` records. `output` gives what came after an offset, for a page that polls. Errors are `{ error, code }`: `terminal-limit` 409, `unknown-shell` 400, `no-terminal` 404, `terminal-unavailable` 409, `shell-failed` 409 (the shell or folder wouldn't start), and `not-on-this-machine` 409 when the app's folder isn't here. A restart that a close overtakes starts nothing. Typing or resizing in the second before a shell's exit is reported is ignored.
  - The environment is `withoutServerSecrets(process.env)`, plus `TERM=xterm-256color` and `COLORTERM=truecolor`. The folder is the child's working directory and never goes on a command line.
- **Web.** `packages/web/src/code/terminal/`:
  - `TerminalTab` shows the focused app's terminals as a strip: click to switch, double-click to rename (Enter saves, Escape or a click away cancels), ✕ to close, **+** for the default shell and **▾** for the others. Opening the tab on an app with no terminals starts one.
  - `TerminalView` is the only xterm importer. It follows only the terminal on screen, through `feed.ts`. A browser keeps about 6 connections to one HTTP/1.1 server, and a page already holds `/api/events`, one stream per chat pane (up to 4) and sometimes a browser live view. In the desktop app each stream has a `*.localhost` host name of its own (`streamApiUrl`, `streamsShareHost` in `state/transport.ts`), so there the terminal always streams. In a browser the limit is shared by every tab on the server, so each tab posts its stream count on a BroadcastChannel (`state/streamCensus.ts`, `browserStreamCount` in `state/sse.ts`), and the feed streams while the browser holds fewer than 5 streams and otherwise polls `output`, which shares the connections. A streaming terminal drops to polling (the screen starts again from the buffer) when chat panes opened after it, or another tab, take the connection it was leaving free. It doesn't go back to streaming. A tab that crashes leaves its last count with the others until they reload, which only makes them poll sooner. Hidden terminals keep running and catch up from the buffer when shown. Typing is sent once per animation frame, in order. Its colours are read from the theme when it opens, and again when the OS switches between light and dark (`onColorSchemeChange` in `screen.ts`), so an open terminal recolours. Links open through `openInBrowser`, typed ones (the web-links addon) and OSC 8 hyperlinks (xterm's `linkHandler`) alike, and only http and https ones: anything else a program writes is dropped (`openTerminalLink`). The "Process exited" bar sits below the screen.
  - Keys: Ctrl+` opens the Terminal tab and focuses it, and Ctrl+Shift+` opens a new terminal (Code mode only, `useTerminalShortcuts`). The request waits in the store (`takeTerminalRequest`) until the tab takes it, so a press from another tab still opens one. Ctrl+C copies when there's a selection. Ctrl+V pastes. Ctrl+Tab and Ctrl+1-9 still switch tabs and panes. Alt+digit and Ctrl+Shift+Enter go to the shell (`usePaneShortcuts` skips them inside `[data-terminal]`).
- **Security posture.**
  - **A shell with no approval card.** So the routes exist only on a local server: open or token mode, bound to loopback (`terminalsAllowed` in `cli.ts`). They aren't there in sign-in mode or on a token server listening on the network. The status route answers `not-local` there, and the tab doesn't show.
  - **Never on the peer listener** (`forwardedApi`). `test/routes/terminals.test.ts` checks that every terminal path is a 404 there. Running an app on another machine (the next piece of work) will put it there deliberately, and this section must then say that a paired machine can open a shell with no card.
  - **User-only.** Nothing here is a model tool, and nothing reaches the `PermissionBroker`. In open mode (`npm run serve` with no token) any local process can drive the API, terminals included, as it can already send messages and answer cards. A model whose approved shell command `curl`s an open-mode server could reach a terminal, but it could already run that command.
- **Shutdown.**
  - A clean quit kills every terminal's tree in parallel (`container.close()`, and `settled()` waits for it). The desktop's 2.5 s shutdown wait covers that.
  - `otherbench serve` now handles SIGINT and SIGTERM. It kills the terminals, then exits with 130 or 143 and runs none of the other shutdown, as before.
  - **The desktop app on Windows** runs the server in a job object (`desktop/src-tauri/src/job.rs`) with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, which everything the server starts inherits (a process may still leave it by asking to, `BREAKAWAY_OK`). Killing or crashing the app ends the job. If the server exits on its own while the app runs, a thread waiting on its process ends the job at once, and the same happens when it has to be killed after the shutdown grace. A clean exit takes the limit off, so it leaves running what it did before. There is no restart of the server after a crash, as before. A process the server starts in the moment between its spawn and its assignment to the job isn't in it. `cargo test` checks a crash, a forced stop and a clean exit against a real `cmd` and `ping` grandchild; the app itself hasn't been crashed by hand.
  - **A plain `otherbench serve`, and the desktop app on Linux and macOS,** still leave a terminal's processes running after a crash or a hard kill. On Windows a startup sweep can't find them: once the shell has gone, its orphans have no parent link back to it, and without a job object nothing groups them. On POSIX a sweep by the recorded session ids could, but it would need the recorded start times to rule out a reused id, and it couldn't be tested here, so it isn't built.
- **Apps.** Deleting an app kills its terminals, whether through the route here or a delete that arrives by sync (`killTerminalsOfGoneApps` on `sync-applied`). Changing the app's folder leaves running terminals where they are, and new ones open in the new folder. Nothing about terminals is stored or synced.
- **Installer.** `bundle.mjs` copies `@lydell/node-pty` and its per-platform package beside `cli.js`. `bundle:smoke` starts and closes a terminal, and fails if the bundled server can't.
- **Known gaps.** A terminal opened while the app's folder is on another machine says "not on this machine": running an app elsewhere is the next piece. A terminal's title is its shell's name or the one you gave it, not the running program's.
- **Tests.** Server: `test/terminal/` (`shells`, `kill-tree` against a faked POSIX process table, `manager` against a fake PTY, `live` against a real one, skipped where the PTY doesn't load) and `test/routes/terminals.test.ts`. On Windows `live` also checks that closing a terminal ends a grandchild started through a `.cmd` shim, as `npm run dev` does (shell, `cmd`, node, then a detached node, which closing the ConPTY alone leaves running). `test/cli.test.ts` covers `terminalsAllowed` and the signals. Web: `code/terminal/*.test.tsx` (`TerminalView.test.tsx` stands in for xterm to check the link handler and the theme), `PanelResizer.test.tsx`, `codePanelWidth.test.ts`, and the terminal cases in `CodePanel`, `usePaneShortcuts` and `store` tests. e2e: `code-tab.spec.ts` opens the tab, checks that the prompt names the repo folder, echoes, reloads and finds the output replayed, and drags the panel wider.
