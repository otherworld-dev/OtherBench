# The model's browser (Deck #926)

Spec: `docs/superpowers/specs/2026-10-12-model-browser-design.md`; plan: `docs/superpowers/plans/2026-10-12-model-browser.md`.

- A profile turns on **Browser** (off by default; `toolPolicy.browser`, `browserBlockedHosts`). API and Claude Code profiles alike: Claude Code gets it relayed on its `otherbench_<hex>` server as `browser`, in folder and clean chats.
- One browser per server, a **real Chrome or Edge window** where one can open (`playwright-core` 1.62.1; `OTHERBENCH_BROWSER_PATH` names the build; tried in order Chrome, Edge, Playwright's Chromium, then headless where no window can open, such as a server with no display; `OTHERBENCH_BROWSER_HEADLESS=1` forces headless, which every test uses). It starts on the first call and closes 5 minutes after the last page closes. Each **page** is its own context and so its own window, minimised and out of the way: a chat has its own page, which its replies use, and each sub-agent gets a page of its own (see "Sub-agents" below). A window starts off screen so nothing flashes, then moves on screen and minimises: an off-screen window draws nothing, so the live view would stop, and a minimised one keeps drawing (measured on Chrome 156). A page closes after 15 idle minutes, on Close in the viewer, when a person closes its window, and at shutdown; a sub-agent's page also closes as soon as the sub-agent ends. Deleting a chat closes all its pages.
- **How many.** At most 8 pages are open across every chat (`MAX_OPEN_BROWSERS`, once 4 chats' browsers) and at most 5 in one chat (`MAX_CHAT_PAGES`: its own and one for each of the 4 sub-agents a reply may run at once). A page still starting counts. When a cap is reached, the least recently used page nobody holds is closed to make room, one of the same chat's when it is that chat which is full, never another chat's for that; with none to close the call fails with `browser_busy` naming the cap. The chat's own page keeps its holder rule: the reply that last acted holds it until its turn's signal aborts, and another reply meanwhile gets "This chat's browser is in use by another reply." (compare tabs still share it). A sub-agent's page is only ever its own, so it is never busy for that sub-agent and its parent never waits on it.
- **Saved sign-ins** (`tools/src/browser/profile.ts`). Cookies and local storage are copied into each new context from a profile sealed in the secret store, and saved back when it closes and after a handover, as a three-way merge so pages open at once (two chats', or a chat's and its sub-agents') don't undo each other and signing out sticks. The merge writes back only what a page changed since it opened: a cookie or a site's storage it holds just as it was given them is left as the store has it now, so a sub-agent's page closing late can't put back a cookie another page signed out of, or an older value of one it changed (it used to write back everything it held). It is a copy and not one persistent Chrome profile because the proxy tells pages apart by their credentials, and those are per context. It is separate from the person's everyday browser, so the model is signed in only where someone signed in *here*, and every site still needs its card. *Forget sign-ins* in the Browser panel clears it (`DELETE /api/browser/profile`). A scheduled run gets the sign-ins too, on sites it has a grant for.
- **Cookie boxes** are answered as pages load by DuckDuckGo's Autoconsent rules (`tools/src/browser/consent.ts`, MPL-2.0, three files of it copied by `bundle.mjs`): refuse where offered, otherwise accept. It isn't a tool call, so no broker and no card. Its script lives in the page's world, so a message may be the page's own; all one can do is run code in the frame that sent it and add a fixed note. A new page's result waits up to a second for a box. Sites where the rules don't work leave the model clicking the box itself, with a card.
- **A person on the page.** Clicks, scrolling, typing and pasting on the picture in the Browser panel reach the page (`POST /api/chats/:id/browser/input`), and *Show window* brings the window up. Under `/api` like every other change, so sign-in, the Host and cross-site write checks and the computer-use desktop-only rule all apply; no broker, as it's the person's own doing. While a person has the window, what they open from it (a sign-in popup) stays open; the model's own popups are still closed. **Password fields are emptied for the moment a snapshot is read**, because a snapshot carries field values; nothing else a person types is hidden from the model.
- **`handover {reason}`** is the model's way to stop for a person: the window comes forward, a `kind: 'browser'` ask raises a card and a notification, and the answer returns the page as the person left it. *I'm done* or *Skip*, 10 minutes at most, refused at once in a scheduled run. The model is told never to solve or get round an "are you human" check, and OtherBench deliberately does nothing to hide that the browser is automated (`navigator.webdriver` stays true, Chrome's banner stays). So some sites' checks may fail even for a person.
- **Signals and exit.** Chromium is launched with Playwright's `handleSIGINT`, `handleSIGTERM` and `handleSIGHUP` off, so a running browser does not change how `otherbench serve` stops (with them on, a SIGTERM would close the browser and leave the server running). Chromium still dies with the server: Playwright always installs an `exit` handler which kills the browser's process tree when the server's process exits (`taskkill /T /F` on Windows, SIGKILL to the process group elsewhere). A death that skips `exit` (Ctrl+C or SIGTERM with Node's default handling, a hard kill) relies on Chromium closing when its DevTools pipe to the server breaks instead. Checked on Windows with the headless shell: gone when looked for 1.5 seconds after `process.exit`, and about 4 seconds after the server was killed outright. Not checked on Linux or macOS.
- Commands: open, snapshot, click, type, select, press, scroll, back, close. The model acts on `[ref=eN]` refs from an accessibility snapshot. Every page result says the page text is untrusted.
- **Long pages come in parts** (`tools/src/browser/snapshot.ts`). A snapshot over 40,000 characters (about 10,000 tokens) is split at line breaks into parts of at most that, so one result holds no more than that and a one-line note. Every command answers with part 1; `snapshot {part}` gives the others. A result with more than one part carries `part` and `parts`, and its snapshot ends with a note saying which part it is and, until the last, "use snapshot with part N+1" (scrolling never changes it: the snapshot is the whole page, not the viewport). Each call takes a fresh snapshot and serves the part asked for, so a page that changes between calls can shift its parts; the refs are always read from the whole of the fresh snapshot, so a ref from any part can be acted on. A part past the end is `bad_call` naming how many parts there are now. The card for `snapshot` with a part names it ("read part 3 of the page").
- **The host is judged one way only.** It is taken from the URL by the WHATWG parser and canonicalised (lower case, trailing dot, IDN, numeric and hex IPv4, bracketed and v4-mapped IPv6) in core's `browser-hosts.ts`. The same shared test vectors are run through the broker and through the proxy, so the two cannot drift apart.
- **The proxy is the enforcement point.** All browser traffic goes through an OtherBench proxy on 127.0.0.1 (a user per page, so per chat and per sub-agent, and a per-launch password). It resolves names itself, checks the address after DNS on every request, then connects to the IP it checked, so DNS rebinding has nothing to swap. It refuses loopback, private, link-local, CGNAT, multicast and reserved addresses, local names and the profile's blocked sites. It does **not** enforce per-site grants: a page loads other sites' sub-resources, and a page may move itself to another site without a card. The card is about what the model asks for, not a fence round the page.
- **This computer's own addresses are refused too.** A public address assigned to one of this machine's interfaces passes the "is it public" check, yet reaching it reaches OtherBench's host from inside. The proxy reads `os.networkInterfaces()` (every 60 seconds, and again at once for an address which is not in the list) and refuses each of the machine's own public addresses, an IPv4 one also in its v4-mapped, NAT64 and 6to4 forms, and anything in the /64 of each of its public IPv6 addresses, which covers the devices sharing that network. No option lifts this; the test allowance for 127.0.0.1 is unaffected because 127.0.0.1 is never public. **The gap that remains:** another device on the LAN with a global IPv6 address outside those /64s (a second prefix or subnet, a routed prefix behind another router) still counts as the internet, as does the router's own public IPv4 address where it answers from inside.
- **No UDP round the proxy.** WebRTC is held to proxied connections with two switches, because the builds read different ones: the headless shell reads `--force-webrtc-ip-handling-policy=disable_non_proxied_udp`, and full Chromium, Chrome and Edge read `--webrtc-ip-handling-policy=disable_non_proxied_udp`. Both are always passed, with `--disable-quic` as a second line. The integration test gathers WebRTC candidates against a STUN socket on 127.0.0.1 and expects no packets; it was run against the headless shell, full Chromium, Chrome and Edge (4 packets on full Chromium with the first switch alone, none with both).
- **Lookups are bounded.** At most 3 name lookups run at once (`dns.lookup` holds one of libuv's 4 threads each) and one that takes longer than 5 seconds, waiting included, is refused. The "N requests to blocked or local addresses were refused" note counts policy refusals only, not names that do not resolve or malformed requests.
- **Approvals are per website and bound to the page described.** `ToolSpec.describeCall` works out the host before the broker decides. "For this chat" and "Always" grants are pinned to `{ host }`. Under "ask on mutate", snapshot/scroll/close need no card. An approval carries the navigation id and the ref snapshot generation of the page the model was shown (not the page's address, so no query string reaches the audit that way), and both are re-checked synchronously right before acting. If the page moved: "The page moved to <site> since this was approved. Nothing was done: ask again." A ref which is not in the latest snapshot is refused before any card. One window remains: the check reads Playwright's client-side view of the page, which lags a navigation Chromium has just committed by one round trip.
- **The profile's site list** (`Profile.browserAllowedSites`, migration 042, `profile.browser_allowed_sites`; empty by default). Websites the browser may use without a card, in chats, scheduled runs and the chat's sub-agents. An entry is a host name, `example.com`, which matches that host only (not `www.example.com`), or `*.example.com`, which matches its subdomains at any depth but **not** `example.com` itself (as in a TLS certificate and the sandbox's host list; list both to allow both). `core/src/domain/browser-sites.ts` checks entries (`parseAllowedSite`) and matches them (`siteListEntryFor`), spelling hosts with `normaliseHost` as the grants do (lower case, punycode, no trailing dot). It refuses a scheme, path, query, port, userinfo, any `*` but a leading `*.`, IP addresses in any spelling, `localhost` and the local-network names, a bare top-level domain and public suffixes. **No Public Suffix List is shipped** (`tldts` is in `node_modules` only as a test dependency of jsdom), so a public suffix is: a name with no dot, a registry second level (`co`, `com`, `org`, `ac`, `gov`, `or`, `ne` and a few more) under a two-letter country code (`co.uk`, `com.au`, `or.jp`), or one of a short list of other multi-part suffixes, mostly hosting platforms (`github.io`, `herokuapp.com`, `vercel.app`, `pages.dev` and so on). A suffix outside those rules (`k12.ca.us`) gets through; the entry still only skips the card for the sites it covers. The profiles route takes the list as a top-level `browserAllowedSites` (not in `toolPolicy`), at most 200 entries, and answers 400 naming the first bad entry. **How it is enforced:** `PermissionBroker.decide` consults it for a browser call after every refusal (the policy switch, the plan gate, the blocked sites, local names and private addresses) and returns `allow` with `grantedBy: 'site_list'` and the entry that matched; `auditGrantedBy` writes that to the audit trail as `site_list:<entry>`, which the Inspector labels "profile site list". It is read from the store on every call, under `ctx.profileId`, the profile grants are matched under, so a sub-agent uses its parent reply's list and never the one of the profile it runs as. Entries are parsed again before matching, so one that skipped the route (a synced or hand-edited row) matches only if it would be accepted now. The proxy never reads the list, so a listed name that resolves to this machine, the LAN or link-local is still refused when the page connects (`tools/test/browser/site-list.test.ts`). The editor shows the field under Browser with a warning that these sites are visited without asking, scheduled runs and sub-agents included; the Inspector's Tool grants section shows the chat's profile's list above its grants while the browser is on.
- **Claude Code runs only ticketed arguments.** The PreToolUse gate keeps the approved (described) arguments as an approval ticket; OtherBench's MCP server runs only those, once. No ticket gives "OtherBench has no approval for this call."
- **Page-derived text is sanitised and labelled** wherever it reaches a card or the thread (web `viewer/browser.ts`: page text cleaned for display, the model still sees the raw text), so a page can't pass itself off as OtherBench's own words.
- The viewer's **Browser** item shows a live JPEG stream (`/api/chats/:id/browser/live`, 5 fps at most) that takes input. It shows the chat's own page. **While sub-agents have pages**, they are listed above it ("This chat's page", then "Sub-agent: <label>" for each, the label cleaned as page text is, the site as the tooltip), and picking one shows that page: its frames, address and title, and input, Show window and Close (labelled "Close page") act on it. When the sub-agent's page closes the panel goes back to the chat's own. Every state the server sends carries `page` and `pages` (the chat's open pages, its own first), so the list stays current on every watcher. The routes take `?page=`: `main` (the default) or a sub-agent page's 16-hex id from that list, anything else is 400; `DELETE /api/chats/:id/browser` with no `page` closes every page of the chat. Not on the peer listener: a chat running elsewhere says which machine has its browser, and its window opens on that machine, so the panel can't be used for it from here.
- Tests: unit tests per module, `packages/tools/test/browser/browser.integration.test.ts` (real Chromium against a loopback fixture; skipped with a logged reason when none starts, but a failure when `CI` is set; `OTHERBENCH_BROWSER_PATH` runs it against another build), `packages/web/e2e/browser.spec.ts` (`OTHERBENCH_BROWSER_ALLOW_LOOPBACK_PORTS` lets the e2e server reach its fixture site on `OTHERBENCH_E2E_SITE_PORT`, default 4797; OtherBench's own API and peer ports are taken out of that list with a warning). No test browses the internet. CI installs `chromium-headless-shell`.
- **Accepted as they are:** an element whose name Playwright writes unquoted as `/regex/` gets no ref and cannot be acted on; parallel calls described on one snapshot fail with `stale_ref` after the first, as each result replaces the snapshot; `select` values and the query string of an `open` URL go to the local audit unredacted (typed text is redacted).
- **Beside the other features (integration, feat/cowork-parity-all):**
  - **One `host` grant constraint, with the sandbox's network cards.** A browser grant and a `sandbox_network` grant are stored and matched by the same broker rules: `alwaysConstraintFor` (an "Always" answer must carry exactly `{ host }`, the card's own, and is stored canonical), every-key matching, and no match for a grant with no constraint. The grant's source is part of the match, so a browser grant for `pypi.org` never lets the sandbox reach it and a network grant never lets the browser open it. The route's `parseConstraint` takes one key of 1-253 characters for both, and the card's "Always" sends exactly that. When the broker refuses to store an answer as a grant (any card: an "Always" naming another site, a shell answer with no command to pin), the person still said yes to that call, so it runs once, and the audit row and the `resolved` event say `once`, not `always`.
  - **One set of host rules.** The sandbox's `canonicalHost` is `normaliseHost` plus the sandbox's own limits, its IPv4 ranges are `isPublicAddress`'s and the local names are one rule (`isLocalNetworkName`: the suffixes in `LOCAL_NAME_SUFFIXES`, and any name with no dot). So the sandbox now also refuses `*.lan` and 192.88.99.0/24, and the browser `*.localdomain` and a name with no dot (`router`, `intranet`: a different machine on every network, so a grant for one would mean a different site wherever OtherBench runs). `packages/core/src/testing/shared-host-vectors.ts` is run against both and pins where they differ on purpose: the sandbox takes no IPv6 literal, no percent-escape, no underscore and no name over 253 characters; the tests-only loopback allowance is the browser's alone (it is for the address 127.0.0.1, never a name). The same file holds resolved addresses for the browser's proxy and the sandbox agent in the VM (`agent-core.mjs` can't import core and keeps its own ranges): the agent lets through 192.88.99.0/24 and the IPv6 special ranges the browser refuses (6to4, Teredo, the RFC 9637 documentation range, discard-only, v4-compatible, and anything outside 2000::/3 that isn't on its list). Pinned, not changed.
  - **Plan mode.** Until the plan is approved a reply may read the page that is already open (`snapshot`, `scroll`, `close`, by command name), and `open` a site that already has a standing grant: a stored grant (this chat's or an Always one, under the profile grants are matched under, so a sub-agent's is its parent reply's) or an entry on the profile's site list. Claude Code's WebFetch is allowed while planning, and this is the browser's equivalent, kept to sites a person already let it use. An `open` with no standing grant is refused with `PLAN_BROWSER_OPEN_REFUSAL` (the plan refusal plus "the browser opens only websites that already have a grant or are on the profile's site list"), audited `deny:plan`, and **never raises a card**: a card would let a planning reply reach a new site. The broker refuses it where it would otherwise have asked (`openNeedsStandingGrant` in `permissions/modes.ts`), so auto mode can't approve it in a card's place either, and in a scheduled run it reaches no more than the run does anyway. The browser's refusals still come first (the switch, blocked sites, local and private addresses). `click`, `type`, `select`, `press` and `back` stay refused with the plan refusal, no card, whatever grants the site has. `allowedWhilePlanning` itself is unchanged: `open` is not on its list.
  - **Scheduled runs.** A browser call that would raise a card is refused with the shared reason (`approval_unavailable`, audited `deny:unattended`). A site on the profile's site list, or with an Always grant (or a grant for the schedule's own chat), works. Reads of the open page need the same: the "Ask on changes" read pass doesn't apply unattended (only `close` keeps it), since nobody sees where the page went. An action that lands on another site (a redirect, a link) returns `{ about, withheld }` in place of the page, with no title, address or snapshot, and forgets the refs; the model reads it with `snapshot`, which works only if that site is approved. The refusal's text and the schedule editor both say what the browser needs.
  - **Sub-agents.** A sub-agent gets the browser only when its parent's profile and the one it runs as both have it on, and may use no site either blocks (the union of the two lists, which goes to the proxy for its page; a page's proxy user keeps every list its holder's calls brought, and starts again when another reply takes the page). Its grants are the parent profile's, like every sub-agent call, and so is its site list; Plan mode's gate is the parent's too. **It has a page of its own** (`BrowserManager`'s `PageOwner`): the tool keys the page on the chat plus `ctx.subagent`, the reply's message id and the sub-agent's call id, both when it describes a call and when it runs one, so the parent and sub-agents running at once never share a page, refs or a holder. It starts with no page open (a `snapshot` before its own `open` gets "No page is open"), its `close` closes only its own page, and its page closes when its signal aborts (the sub-agent finished or was stopped), since nothing can use it after that. Each page has its own proxy user, so the proxy holds each to its own blocked list and counts refused requests for that page's next result. A sub-agent's browser calls show inside its card and don't open the viewer by themselves. Claude Code's own helpers (Task/Agent) aren't API sub-agents: their relayed browser calls carry no sub-agent tag and use the chat's own page, as before.
  - **Claude Code.** `relayTools(policy)` carries the sandboxed `run_command`, the browser and the MCP tools on the one OtherBench server; `relayMcpTools` stays MCP only (what a live artifact may name). A relayed call runs with the current reply's spec and only if it is still the kind of tool the gate approved (`currentRelayed`, fail closed; the browser branch's fall-back to the process's old spec is gone), and the browser then runs only with its ticket. Questions and plan cards go through the same gate untouched.
  - **Remote access.** The state, the live view and the close are under `/api`, so sign-in mode, the Host check and the cross-site write check cover them; none is on the peer listener (`packages/server/test/routes/browser-remote.test.ts`).
  - **Not built:** the sandbox-VM phase. The browser still runs on the host, not in the sandbox, and nothing it loads lands in a chat's folders (no downloads).
- Still to check by hand (spec §8 "Live check"): an API Sonnet profile and a clean Claude Code chat using a real site; a cookie banner and a form; Edge as the fallback through `OTHERBENCH_BROWSER_PATH`; memory with two chats' browsers open, and with all 8 pages open; a reply running two or three sub-agents that browse at once (a window each, the panel's page list and switching between pages, each page closing when its sub-agent ends, and the sign-ins each saved still there afterwards); the 15-minute idle close; Chromium dying with the server on Linux and macOS (see "Signals and exit" for what was checked on Windows); the live view on a phone in sign-in mode; a remote box with a public IP can't reach its own services through the browser (its own addresses are refused, so a site hosted on the same machine as OtherBench will not open). If a live Claude Code browser call answers "OtherBench has no approval for this call.", suspect key order: tickets are keyed on `JSON.stringify` of the raw arguments, and the hook's `tool_input` may order keys differently from the MCP call (it fails closed). A hung Chromium's kill path is tested with a fake only.
